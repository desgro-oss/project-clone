5. Раскладка

Контентная область — 12 колонок, зазор 16px. Единственный блок контента — таблица на всю ширину. Горизонтального скролла у рабочей области нет — горизонтальный скролл только внутри тела таблицы (.tbl--scroll). Отступ таблицы от нижней границы экрана — 24px: это нижнее поле контентной области, собственного margin-bottom у таблицы нет (правило каркаса — низ одинаков для всех типов контента).

Высота таблицы — правило каркаса (Layout .screen--app + Table .dtable--fill): таблица как единственный/основной блок занимает всю свободную высоту экрана за вычетом полей контента, крошек, шапки страницы и тулбара/фильтра. На рабочей области стоит .screen--app (фикс. вьюпорт 100vh), на таблице — .dtable--fill: тело таблицы скроллится внутри, крошки/шапка/тулбар/пагинация закреплены. Вертикальный скролл страницы при этом отсутствует — скроллится только тело таблицы.

Ключ колонки (data-col). Каждая содержательная .th в шапке (23 колонки) и каждая ячейка, которую собирает renderRow, несут data-col="<поле сделки>" — ключ пишет общий cellOpen. Это хук рантайма таблицы: по ключу DSTable.adoptRow сопоставляет ячейку строки, дописанной экраном, с колонкой шапки и приводит строку к текущей форме колонок — порядок после переноса, треки после ресайза, ячейка скрытой колонки уходит на склад строки. Инсеты закрепления новой строке проставляет tbl-pin.js (он ловит вставку строки сам). Своего JavaScript под это экран не пишет: обработчик «Новая сделка» только вставляет строку (TableCell 2.019, Table 1.016).

Скрипт стоит после ds.js (нужны window.DSTable/window.DSPagination, которые ds.js догружает через document.write); рантаймы таблицы сами поднимаются на DOMContentLoaded — позже, чем этот синхронный скрипт, поэтому 50 вставленных строк учитываются ими штатно при первом wire() (порядок для data-sort-rows, тултипы усечения — без обращения к rowsChanged(), он нужен только для строк, добавленных ПОСЛЕ загрузки страницы — см. Table 1.012).

Плоские поля записи — id, name, status/statusTsup/statusOps/statusMon (кортежи §7), restricted, desk, director/manager/tsupEmployee, knr[], gsz, jointness, collateral, corpGovernance[], boardRep, finTpl, signDate/firstDisb/endDate/repayDate, monEntity, и производные из дерева продуктов — mainProductDid, productsDidNames[], productsNames[], balances[], currencies[], isTypeC. Производные поля вычислены из MOCK_DEAL_TREES один раз при генерации и заморожены в записи — в проде их считает бэкенд, реестр не пересчитывает.

Допущения по форматам (нет однозначного ответа в ТЗ): corpGovernance — список строк; boardRep — Да/Нет.

jointness («Совместность») — краткое имя территориального банка, с которым ведётся сделка (DEALS_ENUMS.jointness: ЦА, ЦЧБ, УБ, МБ, ЮЗБ, СРБ, ВВБ, СБ, ПВБ, СЗБ, ДБ — список и порядок с экрана текущей системы; полные имена — DEALS_ENUMS.jointnessNames, подтверждены человеком 25.09.2026), пустая строка — совместности нет. Значение уточнено по макету тайла «Описание сделки» (решение человека 24.09.2026); до того здесь было «Совместная»/«Не совместная». Фильтр «Совместность» берёт варианты из того же справочника.

Распределение 50 сделок покрывает крайние случаи вёрстки: 5 сделок-черновиков без дат (прочерк во всех трёх датах), сделка с максимально длинным наименованием, сделка со всеми 4 валютами ДС сразу (RUB/USD/EUR/JPY — больше в системе не заведено), сделка с 6 балансами, сделка с 4 КНР, инструмент без транша. 3 сделки — restricted: Да, 6 — isTypeC: true.

Вариант «тулбар над таблицей» (.dtable-toolbar + headless-таблица):

  • зона .dtable-toolbar — БЕЗ подложки, над таблицей: слева TableFilter (кнопка «Фильтр» → filter-scrim, чип «Применено: N» — с 05.09.2026 реальный, скрыт при N=0), справа кнопка «Настроить колонки» (ibtn с глифом settings → cols-scrim);
  • таблица .dtable--fill — headless: без .dtable__toolbar, сразу шапка колонок; заголовка «Сделки» и счётчика «128» наверху нет (счётчик остаётся только в пагинации).

Каркас: .tbl[data-table] + .tbl--scroll. Шапка и все строки имеют одинаковый grid-template-columns (8px-разделитель, 23 колонки данных, замыкающий minmax(8px,1fr)). Колонки «Номер сделки» и «Наименование сделки» закреплены (.th--pinned / .tc--pinned, aria-pressed="true" + глиф pin-filled на th__pin).

Закрепление — из коробки (TableCell 2.013, рантайм tbl-pin.js в ds.js): клик по .th__pin в шапке закрепляет/открепляет любую колонку (без переноса в начало). При горизонтальном скролле закреплённые колонки удерживаются у левого края нативным position: sticky; рантайм считает только инсеты left/right и пишет их при изменении состава или ширин колонок — на скролл не подписан. Закреплённые колонки хвостового блока (все колонки правее тоже закреплены) держатся у правого края; крайний разделитель строки прилипает вместе с примыкающей закреплённой колонкой и красится в её фон. Закреплённые колонки перетаскиваются наравне с остальными. Собственного правила смещения у экрана нет.

Колонка «КНР» и страница сделки. Реестр подключает CounterpartiesStore (../data/counterparties-store.js, с mock-counterparties.js и post-api.js) после deals-store.js. Стор читает составы, сохранённые в окне КНР на странице сделки (сервер данных, пока не заведённый, или localStorage, контракт — ../data/API.md), и переносит имена КНР в deal.knr через DealsStore.update. Если хранилище ответило позже рендера строк, экранный скрипт перерисовывает содержимое ячейки «КНР» на событии change. Ячейку он берёт через DSTable.cell(row, 'knr'): так находится и ячейка колонки, скрытой настройкой таблицы. Фильтр по КНР читает тот же deal.knr.

Ширина «Валюты» — 150px. Два кода по три символа — ~104px плюс 32px паддингов ячейки. 44 сделки из 50 несут ровно две валюты, поэтому две валюты видны целиком, а в «+N» сворачиваются только ячейки с тремя-четырьмя. Свёртку делает рантайм таблицы (ds-table.js) по разметке — два и более чипа в ячейке; экран ничего не размечает. Смена ширины — один трек в grid-template-columns шапки и в константе GRID скрипта экрана.

Формат значений: номер сделки — идентификатор, а не величина: выравнивается по левому краю как текст (.tc--numbers в реестре не используется — правый край и табулярные цифры остаются за суммами и долями); даты — ДД.ММ.ГГГГ; пустое значение — прочерк —; валюты — чип на валюту: 3-буквенный код ISO 4217 прописными (RUB, USD, EUR, JPY), без символов ₽/$/€/¥ и без «руб.», чипы не сжимаются (.chip--fit — код показывается целиком, не «R…»); ФИО — «Фамилия И.О.».

Усечение и тултип: все текстовые значения строк несут .tc__text--truncate — одна строка, многоточие по границе колонки. Полное значение показывает тултип по наведению; он навешивается рантаймом таблицы (ds-table.js) на значения ячеек, подписи колонок и подписи чипов и появляется только тогда, когда текст реально не помещается. Своей разметки тултипа на экране нет.

Начальный порядок строк — по дате подписания по убыванию, как заявляет aria-sort="descending" в шапке «Дата подписания»; сделки без даты (черновики) — в конце.

Выбор строк: не предусмотрен ТЗ (нет колонки чекбоксов и панели массовых действий).

Пагинация (реальная, 05.09.2026): колонтитул собирается скриптом экрана напрямую через DSPagination.footer({ info, pager }) (не автопривязкой data-pagination — она не заполняет левый слот) и пересобирается заново при каждом изменении страницы/размера. Левый слот — pgn-info со значением «Сделок: N» (число сделок, прошедших фильтр; без фильтра — все 50). Размер страницы по умолчанию — 20 (при 50 сделках — реальные 3 страницы: «1 из 3» → «2 из 3» → «3 из 3»); доступны все размеры Pagination (5/10/15/20/50/Все). Строки не пересоздаются — видимость переключает hidden на каждом .tbl__row (правило .tbl__row[hidden], TableCell 2.015): строка видима, если попадает в окно текущей страницы по своей позиции в актуальном DOM-порядке (учитывает сортировку — окно считается ПОСЛЕ перестановки строк).

  • Проверка — на «Сохранить» и повторно на каждой правке поля (input).
