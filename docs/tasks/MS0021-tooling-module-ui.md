# Сервисный модуль и независимый UI инструментария (MS0021)

## Коротко

Выделить четвёртую часть проекта — `tooling/`: хаб, протопанель, сервисные
оболочки, общие генераторы и технические сервисы. Отделить её интерфейс от
интерфейса IBP и его дизайн-системы; `.agents/` сосредоточить на работе агента.
Спланировать сервисный UI на React + TypeScript + shadcn/ui со сборкой Vite.

Задача находится на этапе планирования. Реализация, установка зависимостей и перенос
файлов ещё не начаты. Модуль `tooling/` поддержан человеком; по текущему запросу
структура конкретизирована для shadcn/ui и Vite. Детали реализации проверяются пилотом.

## Решение — предложение

### Четыре части проекта

| Часть | Ответственность | Граница |
|---|---|---|
| `design-system/` | Компоненты, токены, темы и правила IBP, документация самой ДС | Владеет UI продукта; не импортирует сервисный UI для своей работы |
| `apps/` | Модули и концепты продукта, виджеты, данные, паспорта, сценарии и комментарии конкретного прототипа | Продуктовая разметка остаётся на IBP DS |
| `.agents/` | Роли, команды, скиллы, правила, уроки, координация генерации и приёмки | Вызывает сервисные CLI; не хранит браузерный интерфейс инструментария |
| `tooling/` | UI и логика работы с прототипами: хаб, панель, обозреватели, общие форматы, генераторы и transport | Собственные компоненты, токены, тема, иконки и проверки |

Название `tooling/` предпочтительнее `services/`: сейчас большая часть сервиса
работает локально в браузере или CLI, а не как постоянно запущенный backend.
Пользовательское название — «Инструменты прототипирования»; `Studio` возможно
как название интерфейса, но пока не утверждено.

Это один модуль в текущем репозитории. Отдельный репозиторий, публикация npm-пакетов
и многоуровневый монорепозиторий не требуются. Дерево — целевой эскиз, не опись
существующих файлов. `design-system-react/` в текущий репозиторий этой задачей
не копируется: его появление показано как будущее развитие ДС. Две папки ДС
относятся к одной логической части проекта, а не создают пятый сервисный модуль.

**Где лежит shadcn.** В `tooling/src/ui/primitives/` находятся обычные исходники
нужных компонентов: Button, Dialog, Tabs и других. CLI shadcn добавляет их в
наш код; вся библиотека отдельным вложенным репозиторием не копируется.
В `tooling/components.json` алиас `ui` направляется на этот каталог, например
`@/ui/primitives` при `@ → tooling/src`. Расположение настраивается штатно:
[shadcn — components.json](https://ui.shadcn.com/docs/components-json).
Подход с передачей исходного кода описан в
[shadcn — Open Code](https://ui.shadcn.com/docs).

React, выбранные primitives-зависимости, Vite и Tailwind устанавливаются через
`tooling/package.json` в `tooling/node_modules/`. Исходники UI и lock-файл
хранятся в git; `node_modules/` — нет. Готовую file-совместимую поставку `dist/`
предлагается хранить в репозитории, чтобы получателю не требовалось устанавливать
зависимости. Актуальность сборки проверяет tooling-check по манифесту/хэшам.

Внутри панели разделить три слоя:

1. **UI** — отображает состояние и вызывает операции; не ищет продуктовые
   элементы напрямую и не отвечает за запись файлов.
2. **Ядро и storage** — сценарии, номера состояний, комментарии, черновики,
   детерминированные зеркала, сохранение и обработка конфликтов.
3. **Bridge и DS-адаптер** — воспроизведение и запись действий на продуктовой
   странице, измерения, инспекция, принудительные состояния и темы продукта.

Ядро не зависит от UI-библиотеки. Сервисный UI может читать метаданные IBP DS
через адаптер, но не использует её кнопки, поля, модалки и CSS для собственного
оформления. Изменение UI не должно потребовать переписывания формата сценариев.

### Харнес: один вход сейчас, два отделимых маршрута в будущем

Требование человека: работа с продуктом и разработка tooling долго живут в
одном `.agents/`, но добавляются так, чтобы позже каждый маршрут можно было
вынести в самостоятельный харнес или инструмент. Сейчас реализуется внутренняя
граница ответственности, без двух репозиториев, систем плагинов и публикации пакетов.

Предлагается сохранить существующие каталоги ролей, команд, скиллов и tools.
Не нужно немедленно переносить все продуктовые файлы в новый подкаталог.
Лёгкие профили `.agents/routes/product.md` и `tooling.md` перечисляют для своего
маршрута: вход, роли, инструкции, область записи, результаты и проверки. Это
описания для маршрутизации, а не новый исполняемый фреймворк. Имена файлов —
предложение; принцип независимости маршрутов обязателен.

| Слой харнеса | Содержание | Разрешённые зависимости |
|---|---|---|
| Общая координация | Вход пользователя, выбор маршрута, формат задачи/handoff, базовые правила файлов и запуск нужных проверок | Ссылки на точки входа обоих маршрутов; общие правила не содержат DOM-рецептов IBP или компонентов shadcn |
| Продуктовый маршрут | Роли screen-builder/reviewer, подбор DS-компонентов, композиция, продуктовые спеки и приёмка | Общие правила, выбранная продуктовая ДС, apps; сервисные операции — через публичные CLI/API tooling |
| Маршрут tooling | Собственные роли tooling-builder/reviewer, React/shadcn/Vite, сервисные контракты и приёмка | Общие правила, tooling и его публичные адаптеры; не требует продуктовых скиллов сборки экрана |

При реализации соблюдать следующие границы:

1. **Раздельный инструктаж.** Разработка tooling не подгружает весь продуктовый
   чек-лист, ds-lookup и правила HTML-каркаса. Продуктовая сборка не читает
   инструкции shadcn/Vite. Общий вход выбирает профиль до специализированной
   работы; одинаковая роль screen-builder не получает условные правила двух UI-kit.
2. **Собственные роли и приёмка.** Продуктовые роли сохраняют свой контракт;
   новые роли tooling имеют отдельные границы записи и критерии. Общий гейт
   остаётся координатором и вызывает проверки нужного маршрута.
3. **Независимые правила и знания.** Рецепты, чек-листы и уроки продукта и tooling
   имеют явного владельца/scope. Общие — только те, что относятся к обоим.
   Новые специфические правила не дописываются в общий process как обязательные
   для всех; там достаточно указателя на профиль. Старые правила переносятся
   постепенно, когда их касается реализация, с сохранением существующих ссылок.
4. **Точки входа вместо внутренних импортов.** Продуктовый агент может включать
   панель, собирать сценарии и читать комментарии через CLI/API tooling.
   Для этого ему не нужен харнес, который разрабатывает сам tooling.
   Обратного чтения продуктового харнеса из runtime/генераторов tooling нет.
5. **Явные входные данные.** Контекст проекта, адреса ДС/apps/tooling и доступные
   адаптеры поступают через манифест/resolver. Маршрут tooling не получает
   скрытую обязательную зависимость от банковских экранов; IBP-специфика
   остаётся в адаптере и тестовых материалах интеграции.
6. **Список для будущего выноса.** В справке маршрута tooling фиксируются его
   собственные файлы, минимальная общая часть, CLI/API и внешние требования.
   Будущий перенос сводится к переносу этого набора, выбору способа поставки
   общей части и настройке путей. Сейчас общие файлы не дублируются.

После будущего разделения продуктовый харнес сможет использовать готовый tooling
без харнеса его разработки. Харнес разработки tooling сможет работать с модулем
tooling и демонстрационными адаптерами без продуктовых ролей, рецептов и глоссария.
Это целевое свойство архитектуры; фактический вынос в отдельный инструмент —
будущая отдельная задача.

У витрины отделить сервисную оболочку от демонстрируемого виджета. Виджет
продолжает рендериться в IBP DS; оболочка использует библиотеку tooling.
То же относится к замороженному DOM в спеках: новое оформление viewer не
должно менять продуктовый снимок. Для демо рассмотреть отдельный iframe-документ;
возможность взаимодействия с ним по `file://` проверяется отдельно.

### Изоляция интерфейсов

- Для панели основной кандидат — один собственный custom element с Shadow DOM:
  сервисные CSS и компоненты живут внутри, bridge работает со страницей снаружи.
  Shadow DOM не требует применения Lit.
- Собственные значения сервисных токенов; настройки темы tooling и темы IBP
  хранятся отдельно. Наследуемые шрифты и CSS custom properties на границе
  задаются явно: Shadow DOM не сбрасывает их автоматически.
- Простого префикса CSS недостаточно: у библиотек могут совпасть `.btn`, `.tabs`
  и переменные `--primary`. Tailwind preflight и стили библиотеки не загружаются
  в продуктовый `document`.
- Проверить работу меню, диалогов, подсказок и фокуса внутри shadow root.
  Порталы и document-level auto-init — обязательная часть пилота.
- Сервисные клики не попадают в рекордер и не становятся целями инспектора;
  горячие клавиши сохраняют приоритет ввода и существующих окон страницы.
- На хабе допустим обычный документ на той же библиотеке. Не делать iframe
  обязательным способом размещения всей панели: ей нужен доступ к странице.

### file:// и локальная поставка

Сохранить открытие проекта двойным кликом как исходное ограничение. Все
зависимости, стили, иконки и шрифты поставляются локально с закреплёнными
версиями. CDN в готовой поставке не нужен. Сборка для автора допустима как
предложение, обязательный dev-server для просмотра — отдельное решение человека.

Если исходники используют ESM, итог панели должен быть собран для обычного
`<script>` (например, IIFE), без runtime-import, fetch исходников и зависимости
от localhost. Обычная Vite-сборка сама по себе этого не гарантирует.
Ограничения модулей при локальном открытии описаны в
[документации JavaScript modules](https://developer.mozilla.org/en-US/docs/Web/JavaScript/Guide/Modules).

Сохранение остаётся отдельным контрактом: выбор папки через File System Access,
черновики и экспорт при отсутствии доступа, очередь, слияние и проверка записи.
Не менять идентификаторы приложений и ключи localStorage/sessionStorage/IndexedDB
без миграции. Временный localhost-сервис подготовки dev-spec не превращать
в обязательный сервер просмотра прототипов.

### Vite — разработка и готовая поставка

Vite находится в devDependencies `tooling/package.json`; конфигурация —
`tooling/vite.config.ts`. Он запускает среду разработки и собирает исходники
React/TypeScript и CSS в браузерные файлы. Типы отдельно проверяет TypeScript;
успешная сборка Vite не заменяет проверку типов.

| Кто и когда | Действие | Что получает |
|---|---|---|
| Разработчик меняет tooling | `npm --prefix tooling run dev` | Локальную страницу разработки с быстрым обновлением UI |
| Разработчик готовит обновление | `npm --prefix tooling run build` | Готовые JS/CSS/assets в `tooling/dist/` |
| Человек смотрит нынешний HTML-прототип | Двойной клик по HTML, затем кнопка или горячая клавиша панели | Прототип и готовую панель без терминала, установки npm и запуска сервера |
| Человек смотрит будущий React-проект | Серверный режим, уже принятый в том проекте | Тот же tooling с адаптером React-ДС; автоматический запуск сервера в эту задачу не входит |

Имена npm-скриптов и выходных файлов — планируемый контракт. Vite не требуется
устанавливать получателю готового HTML-портфеля: runtime React и UI-зависимости
для панели включаются в поставляемую сборку. Обращений к CDN при просмотре нет.

Для панели и file-хаба настроить отдельные classic-script/IIFE-входы.
В Vite library mode формат IIFE поддерживается; панель и хаб можно собирать
отдельными проходами из одних исходников. Требования: без незакрытых external
импортов React, runtime dynamic import и modulepreload, все пути до assets
разрешаются загрузчиком относительно поставки; данные читаются через нынешние
JS-зеркала. `panel.css` загружается внутрь shadow root, а не в продуктовый document.
Обычный web-профиль предназначен для серверного React-проекта.

Vite по умолчанию готовит сборку для статического HTTP-хостинга: одного
`base: './'` недостаточно, чтобы подтвердить совместимость с file-просмотром.
Реальный запуск без сервера и сети — обязательная проверка Э1, до миграции.
Источники: [Vite — Getting Started](https://vite.dev/guide/),
[Building for Production](https://vite.dev/guide/build.html),
[build.lib и форматы поставки](https://vite.dev/config/build-options.html#build-lib).

## UI-библиотеки — сравнение

Проверено по официальной документации 30.10.2026. Вес сборки и стоимость миграции
не измерялись; оценки пригодности ниже — архитектурное суждение, не benchmark.
shadcn и Basecoat — библиотеки компонентов, Lit и Svelte — средства построения UI;
это разные уровни стека.

| Кандидат | Что даёт | Цена для проекта | Вывод |
|---|---|---|---|
| **Basecoat + vanilla JS** | Близкий к shadcn визуальный язык, готовые HTML/CSS-компоненты, JS для интерактивных частей | При использовании готового CSS не нужен React; сложное состояние остаётся нашим; совместимость JS с Shadow DOM ещё не доказана | Резерв при приоритете минимальной сборки и file-просмотра |
| **React + shadcn/ui + Vite** | Компоненты с доступным исходным кодом, композиция, готовые Sidebar, Command, Sheet, Tabs и другие | React, сборка, Tailwind; для локальной панели нужны отдельный output и настройка порталов в shadow root | **Актуальная рекомендация агента с учётом перехода продукта на React** |
| **Svelte + shadcn-svelte + Vite** | Похожий подход и набор компонентов в Svelte; компилируемые компоненты | Новый стек и сборка; это отдельный проект, не оригинальный shadcn/ui; порталы и file-output также требуют проверки | Альтернатива при развитии инструментария в насыщенное состоянием приложение |
| **Web Awesome; Lit по необходимости** | Готовые web components, темы и компоненты без привязки к React; Lit удобен для собственных реактивных компонентов | Иной визуальный язык, проверка бесплатного набора и локальной упаковки; Lit сам по себе не готовый UI-kit | Резерв при приоритете web components и изоляции |

Основания: [Basecoat — установка](https://basecoatui.com/installation/),
[shadcn/ui — подход](https://ui.shadcn.com/docs),
[shadcn/ui — Vite](https://ui.shadcn.com/docs/installation/vite),
[shadcn-svelte — подход](https://www.shadcn-svelte.com/docs),
[shadcn-svelte — Vite](https://www.shadcn-svelte.com/docs/installation/vite),
[Web Awesome — состав и установка](https://webawesome.com/docs/),
[Lit — назначение](https://lit.dev/docs/).

**Актуальная рекомендация — React + TypeScript + shadcn/ui для tooling.**
Basecoat был предпочтителен для сохранения исключительно HTML/JS-стека.
После уточнения о React-направлении выгоднее сразу делать компоненты сервиса
и управление его состоянием на React, чтобы не переписывать этот слой второй раз.
Это выбор удобства сопровождения и развития; меньший вес относительно Basecoat
не заявляется. Для сборки кандидат — Vite, без необходимости добавлять full-stack framework.

Соседний проект `../ibp-design-project-react/` обследован только чтением.
В его `project.json → reactKit` есть второй renderer `react-uikit`,
`design-system-react/package.json` содержит React 18.2 и MUI 5, корневой
`package.json` — esbuild и TypeScript. README, строки 90–103, уже предусматривает
локальный сервер для React-страниц. Это подтверждает техническое направление,
но не отменяет автоматически требование file-просмотра в текущем репозитории.

Границы при таком выборе:

- Продуктовые React-экраны используют `@sber-ibp/uikit`; tooling использует shadcn.
  Перенос продукта на React не означает замену его ДС на shadcn.
- `core`, `storage` и контракт bridge не импортируют React. Панель монтируется
  отдельным React-root в собственном host; она может работать поверх HTML-страницы
  без предварительной миграции всех экранов — подход поддерживает
  [документация React](https://react.dev/learn/add-react-to-an-existing-project).
- Для React-страниц предусмотреть отдельный адаптер жизненного цикла и устойчивые
  точки взаимодействия; не зависеть от React Fiber и внутренней структуры компонентов.
- Оверлеи панели направлять в контейнер внутри её изолированного корня. Например,
  [Radix Portal](https://www.radix-ui.com/primitives/docs/utilities/portal)
  позволяет задать container вместо document.body; focus, события и вложенные
  продуктовые окна всё равно требуют проверки пилотом.
- Совместимость версий проверить до генерации компонентов: соседняя DS пока на
  React 18.2. Не обновлять её React/MUI только ради выбранной версии shadcn.
  Стратегия общих либо автономных browser-бандлов фиксируется после пилота.
- Поддержать два режима поставки одного tooling: обычную серверную сборку для
  React-проекта и локальный classic-script bundle для HTML-портфеля, если file-просмотр
  остаётся обязательным. Две реализации UI для этого не нужны; стоимость двух
  режимов проверяется до масштабной миграции.

Текущий запрет React в правилах HTML-проекта не изменён; перед реализацией
ограничить исключение каталогом tooling и сохранить правила продукта.

Shoelace для новой реализации не брать: официальный сайт сообщает об окончании
активной разработки и переходе на Web Awesome
([источник](https://shoelace.style/)).

## План миграции

Реализация состоит из трёх этапов ниже. Внутренние подшаги не превращаются
в дополнительные этапы: каждый этап даёт рабочий результат для осмотра.
После отчёта и приёмки — остановка; следующий этап начинается после решения
человека продолжить. Внутри этапа проверки и исправления доводятся до результата.

Для `project.json` предложить явный раздел tooling с путями UI, runtime,
инструментов и viewers; актуальные поля `protoPanel`, `hub`, `localKit`,
`screenMap`, `knowledgeBase` на переходе читает единый resolver. Не заводить
два независимо редактируемых источника путей.

  харнеса или создание отдельного приложения для агента. В этой задаче —
  только отделимые маршруты внутри существующего `.agents/`.

## Критерии приёмки

- По каталогам и манифесту однозначно видны четыре части проекта и владелец каждой функции.
- Хаб и панель используют общий сервисный UI-kit; их оформление работает без CSS и рантаймов компонентов IBP DS.
- Bridge к IBP DS выделен явно; продуктовые превью и снимки сохраняют исходную DS-разметку.
- Продуктовые страницы не импортируют исходники выбранного фреймворка и сервисные глобальные стили.
- Корневой `index.html`, продуктовые URL и ссылки возвращения на хаб сохраняют работу; переходные адреса viewers покрыты проверкой ссылок.
- Проверены обычный экран, концепт, страница ДС, хаб и автономная dev-spec; включение панели не меняет продуктовые стили и состояния.
- Работают Overlay/docking, resize, горячие клавиши, Flows, Fix State, номера состояний, Comments, System, карта, Devmode и переключение темы продукта.
- Форматы YAML/MD, JS-зеркала и существующие public API сохраняются либо имеют явный совместимый адаптер; ключи хранения мигрируют без потери черновиков.
- Проверены отказ доступа, экспорт без папки, повтор записи, конфликт правок и отсутствие дублирования комментариев/состояний.
- Просмотр по `file://` работает без сети и dev-server; подготовка и просмотр dev-spec сохраняют свои отдельные режимы.
- Пилот фиксирует raw и gzip размеры JS/CSS с зависимостями и сравнивает их с текущей поставкой; приемлемый бюджет утверждается по замеру.
- У каждого из трёх этапов есть рабочая точка просмотра, перечень реализованного, проверок и ограничений; следующий этап не начинается автоматически после отчёта.
- Компоненты shadcn находятся в tooling/src/ui/primitives, внешние зависимости — в tooling/node_modules; готовый просмотр не требует node_modules или запуска Vite.
- В `.agents/` есть отдельные входы продуктового и tooling-маршрута; у каждого указаны свои роли, инструкции, область записи и проверки. Общая координация сохраняется.
- Контекст разработки tooling не требует продуктовых скиллов сборки и правил оформления IBP; продуктовый контекст не требует shadcn/Vite. Общие и специализированные документы разделены по владельцу.
- Продуктовый харнес использует готовый tooling через публичные CLI/API и не зависит от харнеса его разработки; tooling не импортирует внутренние файлы продуктового харнеса.
- Подготовлен перечень файлов и общих зависимостей для будущего выноса tooling-харнеса; в нём нет неоговорённых обязательных продуктовых ролей, рецептов или доменных знаний. Физического разделения сейчас нет.
- У сервисного UI есть собственная проверка клавиатуры, доступных имён, фокуса, оверлеев и изоляции; продуктовые проверки не заменяются исключением всего tooling из контроля.
- Статические и Node-проверки выполняются автоматически; визуальные свойства, focus и реальный `file://` вручную проверяются в браузере и отмечаются отдельно от статики.
- Проверки: `proto-panel.mjs --check`, `proto-panel.mjs --selftest`, `screen-map.mjs --check`, `kit-build.mjs --check` и проверки dev-spec по их справке; после переноса — эквивалентные entrypoints с теми же гарантиями.
- `node .agents/tools/lessons-cli.mjs gate` — `ВЕРДИКТ: OK`; проверка границ tooling включена в маршрут гейта.

## Риски

- Включатель определяет приложение относительно своего расположения; storage использует связанные базовые пути. Прямой перенос ломает идентификацию и сохранение.
- ДС-рантаймы работают в document; подключить прежние компоненты внутри Shadow DOM без переработки не получится.
- Витрина, глоссарий и карта имеют общие генераторы и импорты; порядок переноса должен исключать обратную зависимость tooling от агентной оболочки.
- Инспектор из панели встраивается в экспортируемую dev-spec: замена его CSS или путей может сломать автономную поставку.
- Качество доступности и вес нельзя вывести из названия библиотеки; их подтверждает пилот на наших компонентах.
- В рабочем дереве уже были изменения других задач; при реализации отделять их от MS0021 и не перезаписывать.
